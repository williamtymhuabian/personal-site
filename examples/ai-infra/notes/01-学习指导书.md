# 从一次生成理解大模型推理

这份笔记配合现有实验代码阅读。学习顺序是生成循环、KV Cache、离线引擎、服务端请求。环境操作见[SETUP.md](../SETUP.md)，三组正式实验见[EXPERIMENTS.md](../EXPERIMENTS.md)。

目前完成的是代码与实验方法。笔记中的流程、公式和输入长度示例用于解释实现，不能当作已经取得的GPU测量结果。

## 1. 一段文字怎样变成回答

Tokenizer把文字编码为整数序列。输入张量`input_ids`通常是`[batch, sequence_length]`；模型输出的logits通常是`[batch, sequence_length, vocabulary_size]`。

对因果语言模型，`logits[:, -1, :]`给出下一个位置的候选分数。选择一个token，把它追加到输入，再继续前向计算，就形成自回归生成。

先读`scripts/hf_cache_lab.py`中的`reference()`和`manual_generate()`，对应这四步：准备输入、执行前向、选择下一个token、更新历史。注意`model.eval()`和`torch.inference_mode()`的位置，以及生成何时停止。

自然文本入口使用聊天模板，关闭Qwen3的thinking模板；为了固定任务量，即使遇到EOS也继续到指定长度。因此它适合观察生成过程，不能直接当作完整聊天产品的输出策略。

可以在HF环境单独运行基础生成：

```bash
python scripts/hf_cache_lab.py --model models/Qwen3-0.6B --task baseline --new-tokens 64 --output results/raw/hf-baseline.json
```

检查实际输入长度、生成token和文本。字符数、汉字数与token数不是一回事；改变问题语言或聊天模板，长度也可能变化。

读完后，尝试解释：最后一个输入位置为什么能预测下一个token？固定生成64个token与“输出64个汉字”有什么不同？

## 2. 两条生成路径

不使用缓存时，每一步把当前全部历史重新送入模型。使用KV Cache时，第一次处理完整输入并保留各层Key和Value；之后只输入上一步新生成的token，同时传回历史缓存。

单条、无padding请求，输入长度为L、生成N个token时：

```text
无缓存前向输入：L, L+1, L+2, ...
有缓存前向输入：L, 1, 1, ...
最后一次前向的历史总长：L+N-1
```

第一次完整输入的前向已经产生第一个新token。最后一个生成token不再送回模型，因此最后一次前向的历史长度少一个位置。

后续前向的attention mask需要覆盖历史缓存和当前输入。新的Query仍访问历史KV，缓存减少了重复计算，但没有消除上下文变长带来的全部访问开销。[Transformers缓存说明](https://huggingface.co/docs/transformers/en/cache_explanation)

当前实现限定单请求、无padding和固定生成次数。多请求、滑动窗口、不同缓存接口都需要额外处理，不能直接照搬这一段循环。

## 3. 先核对输出，再解释时间

HF对照脚本使用同一模型、输入和贪心选择，交替测量缓存与无缓存两条路径。需要检查：

- `manual_paths_equal_all_repeats`：每轮两条手写路径的token是否一致。
- `cache_equals_hf_generate`：最后一轮缓存输出是否与HF generate一致。
- `forward_input_lengths`：前向输入长度是否符合预期。
- `runs`：每轮耗时和PyTorch allocated显存峰值。

出现分歧时，先找首次不同的token，再查缓存来源、位置、mask、eval状态和精度。不同矩阵形状与低精度也可能改变接近的候选分数；必要时缩短输入、减少生成步数，用相同固定历史比较logits。

正式矩阵使用精确长度的合成token。`--repeat-prompt`重复的是文本，不能保证指定token数。自然回答和固定工作量实验分别保存，不混为一组。

GPU执行是异步的，计时前后需要同步。HF计时包含模型执行与Python循环，不包括加载、分词和文本解码。先查看每轮原始值，再看中位数；不能仅凭一轮较快就判断优化有效。

## 4. 估算KV Cache占用

对未量化、标准MHA/GQA缓存，忽略元数据、碎片和分配开销，可近似估算：

```text
KV字节数 ≈ 2 × 层数 × 序列数 × 每序列缓存长度
          × KV头数 × head_dim × 每元素字节数
```

这里使用KV头数。GQA中不能用Query头数替代；`head_dim`也应读取模型配置，不总是由hidden_size直接推算。

固定模型配置中的28层、8个KV头和`head_dim=128`，在BF16每元素2字节时，每个token的KV约为112KiB，单条2048位置的KV约为224MiB。这是根据配置计算的数组大小，不是显存实测。[固定模型配置](https://huggingface.co/Qwen/Qwen3-0.6B/blob/c1899de289a04d12100db370d81485cdf75e47ca/config.json)

真实进程还包含权重、临时张量、CUDA上下文和分配器保留空间。共享前缀也可能减少实际物理KV占用，因此要分清理论数组、allocated、reserved和设备总占用。

## 5. 沿一条请求读Nano-vLLM

按SETUP.md安装固定提交后，从调用入口逐步追踪请求：

```text
提交请求 → 序列状态 → 等待与运行队列 → 调度
        → KV块分配 → 模型执行 → 更新结果 → 结束与释放引用
```

重点读以下文件：

- `nanovllm/engine/sequence.py`：已有token、缓存位置和块表如何表示。
- `nanovllm/engine/llm_engine.py`：`add_request`、`step`、`generate`如何推进请求。
- `nanovllm/engine/scheduler.py`：等待、运行、调度和完成后的状态变化。
- `nanovllm/engine/block_manager.py`：空闲块、引用计数、分配和复用。
- `nanovllm/engine/model_runner.py`：prefill、decode准备和实际模型执行。

从项目根目录搜索：

```bash
rg -n 'def (add_request|step|generate|schedule|postprocess|preempt)' third_party/nano-vllm/nanovllm
rg -n 'num_cached_tokens|block_table|ref_count' third_party/nano-vllm/nanovllm/engine
```

没有rg时用编辑器搜索。源码位置以固定提交为准，不依赖主分支的行号。

画请求生命周期时，给每个箭头写上对象和状态变化。重点回答：请求何时进入运行队列？资源不足时如何处理？结束时释放的是什么？引用释放为什么不一定意味着缓存内容立即被擦除？

调试日志是可选练习，目前工程没有附带修改上游调度器的补丁。若需要观察，先在自己的分支增加可关闭日志，记录阶段、请求编号、输入长度、缓存位置和队列长度。正式计时前关闭，避免改变测量条件。

## 6. 批请求与CUDA Graph

Nano实验固定输入输出长度，比较提交请求数和eager/graph模式。输入每轮变化，对应模式的输入hash保持相同；每个组合单独启动进程。

整批输出吞吐量等于实际输出token数除以整批完成时间。提交八条请求不保证每一步都执行八条，请求还受调度预算与缓存容量约束。

CUDA Graph通过捕获和重放工作序列减少部分主机提交开销，受形状、内存地址和元数据等条件约束。它是否有收益，需要由对应负载下的结果判断。

Nano计时包含主机调度与输出解码，HF计时不含最终文本解码，两组不直接计算跨引擎加速倍数。固定输入、长度、版本、精度和计时范围以后，才讨论内部对照。

Nano脚本使用温度0.6的采样和固定输出长度，不用它验证HF贪心输出的一致性。同一个seed也不能保证不同引擎得到相同采样文本。

## 7. 进入Mini-SGLang服务端

先看[固定提交的结构说明](https://github.com/sgl-project/mini-sglang/blob/9a91cfafe754aa85daee49998176275667eb58f2/docs/structures.md)，再把HTTP入口、文本处理、消息、调度、执行和输出串起来。每个进程负责什么、传递什么、状态由谁持有，都要能在实现中找到对应。

现有客户端运行在服务器本机，服务只监听回环地址。共享和不同前缀请求保持成对的实际token长度一致，所有对照复用同一请求文件。

`max_previous_common_tokens`描述输入之间的共同前缀，不是服务端实际命中数。naive/radix启动参数由操作者记录，客户端不能只靠HTTP证明真实缓存策略。切换时要重启服务，并保存实际启动条件。

流式数据块也不保证等于单个token。当前客户端记录首段非空文本延迟与总耗时，不推算精确TTFT、TPOT或token吞吐量。进一步统计实际命中长度，需要另加诊断记录，不能把输入相似度当作命中证据。

## 8. 常见概念放在一起看

Prefill处理尚未计算的输入位置并建立KV；Decode通常逐步推进活跃序列。计算量与带宽开销受模型、长度、请求数和硬件影响。

KV Cache保存历史Key/Value；Prefix Cache在条件一致时复用不同请求的相同前缀，还需要匹配、引用、容量与淘汰管理。

PagedAttention关注分页KV的组织与访问；FlashAttention关注注意力计算的数据访问和中间结果开销。两者可以组合，不能互相替代。[PagedAttention论文](https://arxiv.org/abs/2309.06180)、[FlashAttention论文](https://arxiv.org/abs/2205.14135)

TTFT需要第一个有效输出token的时间戳；ITL描述相邻输出token间隔；TPOT需要明确首token后的时间和token计数。整批耗时、首段文本延迟与这些指标不能直接互换。少量测量也不足以可靠描述线上P99。

## 9. 数据回来以后继续问什么

先用报告模板写直接观察，再写解释和未排除的原因。可以从一个小问题继续：更长输入下缓存访问占比怎样变化；批请求增加时等待与计算各占多少；前缀长度和容量怎样影响复用。

每次只增加一个可检查的改动。日志、局部一致性断言、命中计数都可以成为起点，不需要立即重写整个调度器。

延伸阅读可从[SGLang论文](https://arxiv.org/abs/2312.07104)开始，记录它解决的问题、机制、实验条件与局限，再回到自己固定的代码版本里寻找对应。报告只写实际做过的工作和测得的结果。
