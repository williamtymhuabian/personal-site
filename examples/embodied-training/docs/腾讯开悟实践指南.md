## 第一层：把强化学习机制跑清楚

本工程新增 `scripts/grid_rl.py`，只用 Python 标准库，在自建7×7网格中进行 Q-learning。状态是坐标与四邻域障碍，目标位置固定；训练三张地图，另外两张地图只用于评测。它是教学热身，不是开悟环境、VLN 或赛事提交程序。

服务器执行：

```bash
python scripts/grid_rl.py --episodes 4000 --seeds 7 19 43 --output runs/grid-rl-001
```

输出包括每个种子的 Q 表、逐 episode 训练记录、按地图/起点列出的评测和全部配置。默认不运行 GPU，也没有预设成功率；本次只执行了小规模代码测试，没有提交服务器训练或开悟跑榜。

读代码时确认三件事：探索概率怎样变化；真正终止时如何停止价值自举；达到人为步数上限的截断为什么区别处理。奖励分为到达目标、碰撞和每步成本，评价还要单独查看成功与碰撞，避免高训练回报掩盖坏行为。

对照随机策略和局部贪心策略；BFS最短长度只作为读取全图的评测参考，不作为智能体输入。Q表能记忆访问过的状态，在新布局失败很正常；需要据此判断下一步是否引入记忆或函数逼近，不能以训练集表现代替泛化。

## 第二层：在开悟跑固定基线

先固定年份、赛道、开发包版本、环境配置、算法与训练预算。用官方提供的可用基线完成采样、更新、权重保存和正式评估；保存原始日志与回放。当前仓库没有2023/2024的参赛代码、获奖模型或该赛道接口，不能据此复现当年的成绩。

确认环境再选择算法：离散导航可比较 Q-learning/DQN 与 PPO；王者荣耀决策通常还涉及结构化动作、可行动作约束、对手和部分可观测性，不能把四方向动作当成完整接口。[PPO原论文](https://arxiv.org/abs/1707.06347) 可用于理解近端更新，但具体赛道基线与实现必须核对开发包。

训练和评估分开：训练奖励、官方得分、胜率、对手集合与评估对局数各自记录。对战结果需要注明英雄/阵容、对手版本和随机种子，不能将训练时对手上的胜率当作通用能力。

开悟账号、比赛环境和算力开放范围以相应赛道/阶段为准。服务器自备训练与平台集群是两种执行安排，不预设所有读者都可免费调用任何环境。

## 第三层：每次只改变一个因素

先不改网络，分别比较奖励、观测和历史记忆。保持动作空间、训练步数和评估对手相同，才容易解释差异。随后比较前馈网络、带历史窗口与循环记忆，再决定是否需要更复杂模型。

每次训练至少保存：实验名、代码/环境/配置版本、种子、实际环境步数、优化步数、总训练时长、检查点选择准则、训练地图/对手集合、验证集合、独立测试集合、官方原始分数和失败记录。训练中断需保存优化器和采样状态；不能把仅保存模型权重称为可无缝断点续训。

课程学习可以从短任务到长任务，但要与相同总环境步数的随机采样对照。多智能体自博弈需要对手快照与评估池，避免只学会打败单一旧对手。奖励塑形不能只看总回报，要检查刷分、循环和过度保守。

## 第四层：迁移的是方法与证据

将游戏中的局部观测对应到机器人当前可获得的传感信息，将技能选择对应到有限动作，将复活/回合结束重新定义为机器人任务后置条件和停止条件。游戏得分、真实机器人任务成功与安全约束需要分别设计。

接入作品一的训练回放记录、作品二的空间记忆检索和作品三的观测校验。先比较无记忆、固定窗口、显式空间记忆；再研究失败驱动补数据与恢复策略。具身任务的训练数据按场景隔离，过去游戏成绩不作为机器人性能证明。

若未来整理软著或专利，分别记录软件实现与具体技术改进。开悟平台、官方算法、公共场景图和常见 RL 方法的使用本身不等于原创发明；候选机制仍需技术比较与对照实验。研发和成果材料见同目录的《创新与成果记录》。
