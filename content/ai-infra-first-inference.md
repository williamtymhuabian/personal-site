最近开始整理 AI Infra 的学习内容。推理引擎、缓存、调度、算子和分布式，每个词后面都有不少东西要看。我暂时把范围收在大模型推理上，先追一个具体问题：输入一段文字后，程序怎样一步步生成回答？

这条线能把模型计算和系统实现接起来。理解一次生成以后，再看显存为什么不够、多个请求怎样一起执行，源码里的设计会更容易对上具体的问题。

## 一次生成里发生了什么

起步准备选 [Qwen3-0.6B](https://huggingface.co/Qwen/Qwen3-0.6B)，先处理一条输入，观察每次前向计算的输入和输出。

文本经过 tokenizer 变成 token ID 序列。模型给出词表上各个候选 token 的分数，也就是 logits；生成循环从最后一个输入位置的分数里选择下一个 token，再把它接到上下文后面。

这里有两个容易混淆的地方。第一，token 数和汉字数、字符数并不相等。第二，最后一个位置的 logits 用来预测接下来的 token，并不是把输入末尾的 token 再输出一次。

我打算先把这段循环自己写出来。暂时只处理单条、无 padding 的输入，用贪心选择固定生成几步，方便逐个核对 token。等这一段清楚了，再加停止条件和多请求处理。

## 缓存到底省掉了哪部分计算

可以先看一个小例子：输入有 4 个 token，继续生成 3 个 token。完整重算时，每次都把当前全部序列送进模型；使用缓存时，第一次处理完整输入，之后只送入上一步新生成的 token。

~~~text
完整重算的前向输入长度：4 → 5 → 6
使用缓存的前向输入长度：4 → 1 → 1
~~~

KV Cache 保存的是各层已经处理过的位置对应的 Key 和 Value。后续步骤复用它们，减少重复计算；新的 Query 仍需要访问历史 KV。随着上下文变长，缓存占用和访问开销也会变化。[Transformers 缓存原理](https://huggingface.co/docs/transformers/en/cache_explanation)

因此，后续前向只输入一个 token，并不意味着模型只看得到这一个 token。实现循环时，位置和 attention mask 也要与历史缓存对应。

第一组实验就围绕这两条生成路径展开。我会先核对输出，再比较耗时和显存：固定模型版本、输入 token、生成长度和采样方式，保存每一步的输入长度与生成 token。出现分歧时，从第一个不同的位置查起，检查缓存、位置、掩码和数值误差。

计时前先预热，并处理好 GPU 异步执行的同步问题。每轮原始结果都保留，短输入和长输入分别比较。缓存能省掉多少时间，要由实际工作负载下的测量回答。

## 带着一条请求读推理引擎

接下来准备读 [Nano-vLLM](https://github.com/GeeeekExplorer/nano-vllm)。阅读时先追踪一条请求：它在哪里创建，何时进入调度，怎样送到模型执行，生成结束后又怎样释放缓存。

我会沿着这条顺序记笔记：

~~~text
提交请求 → 保存序列状态 → 调度批次 → 分配缓存块
        → 执行模型 → 更新生成结果 → 继续调度或结束
~~~

重点看状态怎样变化。等待队列里存的是什么？一个批次能放进哪些请求？缓存块不够时怎样处理？请求完成以后，哪些资源能够回收？这些问题比按文件顺序从头读到尾更适合我现在的起点。

笔记里除了函数名，还要记下它接收什么、修改什么，以及下一个调用在哪里。必要时给少量请求加上可关闭的日志，先观察状态流转，正式计时再关闭日志。

等离线生成这一段清楚后，再用 [Mini-SGLang 的结构说明](https://github.com/sgl-project/mini-sglang/blob/main/docs/structures.md)去看服务端：请求怎样经过接口、文本处理、调度与模型执行，各个进程之间传递的对象是什么。

## 性能数字先把口径写清楚

后面做实验时，我最想避免的是留下一个没法解释的“每秒多少 token”。

一批请求全部完成的总时间，可以用来计算这批任务的输出吞吐量；它不能直接代替每条请求的首 token 延迟。用户等待第一个 token 的时间、后续 token 的输出间隔和请求总耗时，需要分别记录。相关指标的定义可以对照 [vLLM 的指标文档](https://docs.vllm.ai/en/latest/design/metrics/)。

实验记录还需要说明：计时是否包含模型加载、编译、文本编码和输出解码，输入输出长度是多少，是否忽略 EOS，以及缓存处于什么状态。即使两个程序都输出 tokens/s，计时范围不同，也很难直接比较。

前缀缓存也值得单独做一次实验。我想比较共享同一段 token 前缀的请求与不同前缀的请求，同时记录实际匹配的缓存长度。仅凭一组耗时下降，还不足以判断收益来自哪里；需要把命中情况和缓存开关等条件一起核对。

目前先把逐 token 循环和缓存对照做好。后续文章再放实际代码、每轮测量和遇到的问题。读引擎时发现的疑问，也从这些具体记录里继续往下追。
