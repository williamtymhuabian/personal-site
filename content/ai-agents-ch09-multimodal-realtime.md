学习版修订：2026年10月24日。

一个系统能看懂一张图，不代表它能在图还在变化时正确行动。用户说到一半改了主意，界面刷新了，或者物体移动了，之前的判断即使当时正确，也可能已经不适合现在执行。

本篇对应李博杰《深入理解 AI Agent：设计原理与工程实践》PDF v1.3 第9章“多模态与实时交互”，书内第246—271页，对应 PDF 第254—279页。重点是语音对话、GUI 操作和机器人控制中的持续感知、延迟与反馈。

## “支持多种输入”与“能够实时交互”不同

本章先把“内容正确”和“时机正确”分开。一次判断可能基于旧观察完全成立，但等到动作执行时已经不适用。阅读目标是能够追踪输入发生、计算完成、输出接受和外部动作执行这几个不同时间点。

静态任务可以先收齐材料再生成回答；实时任务中，输入和输出可能同时进行，而且后续输入可能推翻已经形成的计划。

因此除了理解内容，还要管理时间与状态：这条结果基于哪次观察，是否已经过时，用户是否打断，当前动作是否仍然符合目标？只测一张图片的识别准确率，覆盖不了这些问题。

评估也要覆盖完整链路。首次输出很快，但答到一半卡住，用户体验仍可能不好；模型处理很快，但语音分段、网络或工具执行很慢，端到端延迟也不会因此消失。

## 语音架构有不同的能力与代价

级联方案把语音识别、语言处理和语音合成分开，模块易于替换和定位问题，但边界处可能引入等待，也可能丢失语气等信息。把各环节做成流式，可以减少部分等待，但不自动解决所有轮次和打断问题。

端到端模型把多种处理放进更统一的系统，有机会减少中间转换，却也需要新的可观测性与控制方式。端到端不等于全双工：是否能够边听边说、区分自己的声音与用户输入、处理重叠发言，是另外的交互能力。

“快响应”和“深度处理”也可以分工，但接口必须清楚。快速模块不能随意替慢模块编造结论；慢模块完成后，要检查用户目标是否已经变化，而不是把旧答案硬接到新对话里。

## GUI 和机器人需要把观察绑定到动作

GUI 操作需要把“提交按钮”定位到真实界面元素或坐标。结构化元素信息与图像各有适用范围；界面变化后，原来的元素和坐标都可能失效。执行后还应读取新状态，不能把一次点击调用成功当成业务提交成功。

机器人控制增加了物理连续性。高层规划决定目标与步骤，低层控制需要适应传感器、动力学和接触反馈。VLA 把视觉、语言和动作联系起来，但模型输出还要经过适合设备的控制与约束层。

仿真与现实的差异也不只在画面，还包括摩擦、时延、标定和数据分布。某个训练场景完成抓取，不能直接推出它能在所有物体与环境里工作。

## 一条实时链路里有哪些等待？

以语音助手为例，用户的声音经过采集、传输、分段、识别、理解、工具执行与合成，再开始播放。不是每个任务都经过全部环节，也不是每个环节都完全串行。

先用一个纯教学数字理解：若三个必要阶段严格串行，各耗时100、250和150毫秒，那么总等待为500毫秒。若阶段能够流式重叠，端到端时间取决于实际依赖和关键路径，不能继续简单相加，也不能直接取三个数的最小值。

因此要分别测首次可用输出、完整任务完成、打断停止与恢复响应。首次吐出一个无意义音节很快，并不代表完成用户问题很快；识别准确率高，也不表示能够正确判断轮次。

### VAD、ASR、TTS 各自解决什么？

VAD 判断片段中是否有语音活动，ASR 将语音识别成文字，TTS 将文字转为语音。它们分别处理输入活动、内容与输出声音，不能把“检测到静音”等同于“用户已经说完完整意思”。

用户说“我想把那个……蓝色杯子拿过来”，中间停顿可能只是思考。如果仅依据静音阈值切断，就可能在目标还没说完整时行动。语义判断可以提供更多信息，但同样需要评测误触发、等待和打断。

全双工强调输入与输出可以同时处理，不意味着系统天然知道何时插话，也不意味着所有外部动作都能取消。架构能力与交互策略要分别验证。

## 观察、任务版本与动作必须对应

GUI 的一次点击通常依赖某次界面观察。假设观察到按钮在位置A，页面随后滚动了，再按旧坐标点击可能落在另一个元素。执行前重新核对和执行后确认结果，分别解决目标是否仍在和操作是否生效的问题。

机器人链路还应关联图像时刻、坐标参考、标定版本、动作队列与控制反馈。同一“向左5厘米”，在相机坐标系和末端坐标系中可能指向不同方向；时间戳正确也不能补救坐标约定错误。

VLA 常一次预测一段动作。如果执行期间目标变化，当前队列仍可能合法却不再合适。需要比较继续执行、提前截断和重新预测的收益与代价，具体选题可读 [VLA 的8个起步实验](#/post/vla-research-topics-and-starter-experiments)。

### 快慢模块怎样避免互相覆盖？

前台可以维持交互，后台处理耗时查询，但两者应共享任务标识和有效状态。后台完成后先检查原任务是否仍然有效，再决定是否呈现结果。快速反馈可以说明正在查询，不能提前编造查询结论。

若已经执行了外部动作，后续目标变化应进入恢复流程，而不是只删除一段输出。区分“不要再显示旧文本”和“撤回已经发生的动作”，是实时系统中非常实际的工程边界。

## 离线练习：按版本跟踪迟到事件

下面把交互切成带版本号的事件段。打断后提高版本，迟到的旧结果就不能再进入当前输出。练习只处理内存里的字符串事件，使用 Python 标准库。

保存为 `realtime_epochs.py`，运行 `python realtime_epochs.py`。

```python
"""Chapter 9: event ordering simulation; no audio, GUI, robot or network is used."""
class Session:
    def __init__(self):
        self.epoch = 0
        self.partial = ""
        self.accepted = []

    def begin(self):
        self.epoch += 1
        self.partial = ""
        return self.epoch

    def interrupt(self):
        self.epoch += 1
        self.partial = ""

    def receive(self, epoch, text, final=False):
        if epoch != self.epoch:
            return "discarded"
        self.partial += text
        if final:
            self.accepted.append(self.partial)
            self.partial = ""
        return "accepted"


if __name__ == "__main__":
    session = Session()
    old = session.begin()
    session.receive(old, "尚未完成的旧回答")
    session.interrupt()
    new = session.begin()
    print("旧请求迟到结果：", session.receive(old, "继续旧回答", final=True))
    print("新请求结果：", session.receive(new, "只保留新任务结果", final=True))
    assert session.accepted == ["只保留新任务结果"]
    print("已接受：", session.accepted)
```

### 一次正常运行的输出

下面是配套脚本本次实际运行的输出，输入为程序内明确构造的教学数据。

```text
旧请求迟到结果： discarded
新请求结果： accepted
已接受： ['只保留新任务结果']
```

旧结果返回 `discarded`，新结果被接受，最终列表只保留新任务的内容。这个程序演示事件归属判断，不是语音识别、视觉定位或机器人控制模型，也没有测量交互延迟。

这里丢弃的是尚未接受的结果。已经播放的声音、已经提交的表单或已经发生的机械运动，不能靠修改版本号撤回；外部副作用需要单独的状态确认与恢复机制。

可以增加分片序号，处理同一条事件被重复发送；再模拟“结果完成后收到用户打断”，明确哪些输出仍应保留。真实系统还需要缓冲、背压、超时和资源取消，版本号只是其中一个小部件。

### 逐步读懂代码

手工跟踪 `Session`：开始旧任务后 `epoch` 为1；打断后变为2，旧的部分文本被清空；开始新任务后变为3。旧结果仍携带1，与当前3不同，所以直接丢弃。

新任务的文本先写进 `partial`，带有 `final=True` 时再进入 `accepted` 并清空暂存。这个顺序区分了尚未完成的输出与已接受结果，也解释了打断为什么需要清理旧的部分内容。

版本相同只说明属于当前任务，不保证片段完整、有序或不重复。若同一片段到达两次，当前实现会追加两次；若片段2先到、片段1后到，也没有重排。后续可以增加序列号、去重集合和明确的结束标识。

代码没有锁和多线程调度，它用顺序调用演示逻辑。若要处理真正并发，需要让版本检查与接受结果之间保持一致，避免检查后立刻发生打断却仍提交旧输出。

## 评估实时系统时，记录它看见的是哪个世界

一段可用的轨迹可以包含观察标识、时间、任务版本、动作、执行结果和下一次观察。这样才能区分“认错目标”“看对了但动作太晚”“工具执行失败”等不同原因。

还应分别记录首次响应、完整完成、打断生效和恢复所需的时间，并对不同网络与环境条件做测试。不要用一次顺畅演示替代所有条件下的交互质量。

## 分层练习与自测

基础练习：去掉 `interrupt`，但仍调用第二次 `begin`，先预测旧结果能否被接受。新一次开始同样提高版本，因此旧结果仍会失效；显式打断还表达了取消旧部分输出的交互语义。

进阶练习：对当前版本连续提交同一片段两次，观察重复内容，再设计带序列号的去重规则。要区别“网络重复发送”与“用户确实重复说了一遍”。

拓展练习：构造“旧任务已经完成输出后，用户才改变目标”的事件序列。请标出哪些结果只需在界面更新，哪些外部动作需要查询真实状态或补偿。

自测：本地丢弃结果，是否等于停止服务器推理？不是。显示接受规则、资源取消和外部动作取消属于不同机制，可能需要分别实现。

自测：减少推理时延一定提高成功率吗？还取决于观察质量、动作定义与控制稳定性。一个很快但使用错误目标的策略，并不会因为速度快而自动正确。

学习记录可以保留一张事件清单：时刻、任务版本、观察来源、收到的片段和接受决定。用它解释一次迟到、重复或打断，比只记录“实时交互很复杂”更有价值。
