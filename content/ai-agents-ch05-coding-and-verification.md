“代码能运行”和“代码满足需求”之间，隔着一个最容易被省略的步骤：验证。一个补丁可能修好了展示用例，却破坏边界输入；也可能因为改错文件而根本没有作用。

本篇对应李博杰《深入理解 AI Agent：设计原理与工程实践》PDF v1.3 第5章“Coding Agent 与代码生成”，书内第131—161页，对应 PDF 第139—169页。我们把重点放在可检查的开发流程，以及代码怎样成为精确表达和验证想法的工具。

## Coding Agent 的工作对象是整个修改过程

这一章的起点不是“怎样写出更长代码”，而是怎样把需求变成可以反驳候选实现的检查。先理解规格、补丁和验证这三个词：规格定义应该怎样，补丁改变实现，验证提供实现是否满足规格的证据。

一个实际代码任务通常需要定位相关文件、理解接口与约束、提出修改、检查差异、运行验证，再根据失败结果继续调整。生成函数只是其中的一步。

原书讨论文件系统与通用执行能力在开放任务中的价值：中间数据可以留下来，代码可以组合原先没有的处理流程，结果也能被重新检查。但这种架构是一种工程选择，不是所有任务都必须具备任意代码执行能力。

对于一个小而固定的业务操作，受限工具可能更合适；对于需要清洗数据、分析仓库和组织复杂产物的任务，代码与工作区更有组合性。能力范围应与可用的隔离、权限和验证手段一起设计。

## 搜索、编辑与验证各有边界

搜索提供定位线索，不是读完整个项目的替代品。找到函数名后，还需要查看调用方、测试和数据约定，确认它实际参与哪条执行路径。

编辑应有清楚的目标和前置条件。例如，替换文本时要求旧片段唯一匹配，应用补丁时核对基线版本。找不到原片段，可能说明文件已变化；不应自动在另一个相似位置做修改。

验证则从需求建立可执行判断。正常情况、边界输入、无效输入以及相关旧行为，都可能需要覆盖。测试通过说明候选修改满足了这些检查，不能证明没有测试到的所有情况也正确，更不能把一次运行当成形式化证明。

## 先从需求推导检查，再看实现

以区间限制函数为例，输入包括数值 `x`、下界 `lower` 和上界 `upper`。若区间合法，结果应留在区间内；若输入已经在区间内，结果应保持原值；低于下界和高于上界时，应分别返回对应边界。

当上下界相等时，合法输出只有那个端点。当下界大于上界时，必须先拒绝区间，而不能把它悄悄交换。后一条尤其容易被“帮用户修正输入”的实现破坏，因为需求已经明确要求拒绝。

这些条件可以直接推导出测试：低于区间、区间内部、高于区间、等宽区间以及非法区间。测试的来源是行为要求，不是看到代码写了几个分支以后再给它配几个相同的断言。

### 例子测试与性质检查互相补充

例子能显示具体错误：输入5却得到0，很容易理解。性质检查则能覆盖一类输入，例如合法区间内的输出永远满足 `lower <= result <= upper`；对已经在区间内的输入，输出应等于输入。

在合法、有限实数的约定下，还可以检查重复限制同一个结果是否保持不变。这样的性质能够发现一部分缺陷，但也可能让错误实现混过去：始终返回下界满足“结果在区间内”和“重复调用不变”，却违反区间内部保持原值。

所以，多个性质需要共同约束行为。若以后允许浮点数，还要明确 NaN、无穷大和比较规则；不要把有限整数上的结论未经讨论搬到所有数值类型。

### 仓库里的改动为什么不只看一个函数？

假设函数签名不变，但异常类型改了，调用方可能不再正确恢复；假设修补的是一个没有被实际导入的同名文件，局部测试通过，产品行为仍然没有变化。

定位时应沿着调用关系找到真实入口，检查依赖和测试覆盖的路径。修改前记录基线状态，修改后核对差异，再运行与需求直接相关的检查。只有发现新的风险或跨模块影响，才需要继续扩大验证范围。

### 补丁应用也有前置条件

文本替换依赖目标片段。出现两处相同片段时，自动全部替换可能影响不相关行为；找不到旧片段时，可能是文件已被其他人修改。明确失败，比把修改应用到猜测的位置更容易恢复。

真正的并发开发还需要版本控制与合并。它们记录代码变化，但数据库迁移、生成数据与外部服务配置可能需要独立的恢复步骤。代码回退成功，不代表整个系统状态已经回到过去。

## 离线练习：让边界输入揭示错误补丁

需求是把数值限制在指定区间，并在下界大于上界时拒绝输入。只看“负数应该变成0”这个用例，始终返回下界的函数也能通过；加入中间值、超上界和无效区间，差异就显现出来。

保存为 `patch_verification.py`，运行 `python patch_verification.py`。两个候选实现都是手写的，不会调用模型，也不会执行外部生成的代码。

```python
"""Chapter 5: two hand-written candidate fixes, no generated code execution."""
def wrong_clamp(x, lower, upper):
    return lower


def correct_clamp(x, lower, upper):
    if lower > upper:
        raise ValueError("下界不能大于上界")
    return max(lower, min(x, upper))


def verify(candidate):
    cases = [(-2, 0, 10, 0), (5, 0, 10, 5),
             (12, 0, 10, 10), (3, 3, 3, 3)]
    failures = []
    for x, lower, upper, expected in cases:
        actual = candidate(x, lower, upper)
        if actual != expected:
            failures.append({"input": (x, lower, upper),
                             "expected": expected, "actual": actual})
    try:
        candidate(5, 10, 0)
        failures.append({"input": (5, 10, 0), "expected": "ValueError"})
    except ValueError:
        pass
    return failures


def replace_exact(source, old, new):
    if not old or source.count(old) != 1:
        raise ValueError("原文匹配不是唯一，停止修改")
    return source.replace(old, new, 1)


if __name__ == "__main__":
    for candidate in (wrong_clamp, correct_clamp):
        failed = verify(candidate)
        print(candidate.__name__, "通过" if not failed else "失败", failed)
    assert verify(wrong_clamp) and not verify(correct_clamp)
    try:
        replace_exact("a = 1\na = 1\n", "a = 1", "a = 2")
    except ValueError as error:
        print("拒绝含糊修改：", error)
```

### 一次正常运行的输出

下面是配套脚本本次实际运行的输出，输入为程序内明确构造的教学数据。

```text
wrong_clamp 失败 [{'input': (5, 0, 10), 'expected': 5, 'actual': 0}, {'input': (12, 0, 10), 'expected': 10, 'actual': 0}, {'input': (5, 10, 0), 'expected': 'ValueError'}]
correct_clamp 通过 []
拒绝含糊修改： 原文匹配不是唯一，停止修改
```

第一个候选在中间值、上界及无效区间检查中失败，第二个通过这组固定用例。最后的文本替换因为目标不唯一被拒绝，演示了“无法确定修改对象”时的一条明确停止路径。

继续增加一个全负数区间和两个端点用例。再问：如果输入包含小数、无穷大或非数值，需求该怎样定义？不要在实现完成后，才为了迁就已有代码临时修改标准。

### 逐步读懂代码

代码里的 `wrong_clamp` 始终返回下界。它能通过低于下界的测试，甚至能通过上下界相等的测试；中间值和高于上界的测试才揭示它没有实现完整规格。

`correct_clamp` 先拒绝非法区间，再用 `min(x, upper)` 处理上界，用 `max(lower, ...)` 处理下界。先检查区间合法性很重要，否则后面的表达式仍可能给出一个数值，看起来像是正常完成。

`verify` 把实际与预期不一致的输入留下来，还单独检查非法区间是否抛出异常。它没有把“函数抛了任何异常”都当作成功：预期是 `ValueError`，其他异常仍会暴露出来。

`replace_exact` 关注另一个层面：修改对象是否唯一。它不判断补丁逻辑是否正确，只判断这次替换是否有明确目标。把这两个验证放在一起，可以区分“改对位置”和“写对逻辑”。

## 失败结果应该推动下一步，而不是被隐藏

测试失败可能来自实现错误，也可能来自依赖、环境或用例本身。有效恢复首先要分清故障类别，再选择修复、重新配置或请求补充信息。

重试需要边界。遇到暂时性网络错误可以有限重试，但同一个语法错误不会因为重复运行而消失。连续相同失败应触发诊断或停止，而不是无限消耗预算。

对有副作用的操作，还要确认上一轮是否已经部分完成。版本控制能保存和比较修改，不代表所有外部变化都可由一次回退撤销。代码、生成数据和外部服务状态可能需要不同的恢复方法。

## 代码为什么能帮助思考

业务规则写成程序后，输入、分支和异常更容易被逐项检查。统计和计算任务也可以交给确定性工具，避免只靠自然语言心算。但程序实现的规则，仍可能不是用户真正想要的规则。

因此，“精确执行了错误规格”也是一种失败。开发流程需要在需求、实现和验证之间建立对应关系：哪段代码满足哪条要求，哪条检查能发现它被破坏。

原书还讨论生成多媒体、系统适配和创建新 Agent。它们共同展示代码的组合能力；生成出来的程序仍需独立检查，不能因为由另一个 Agent 创建就自动继承可信性。

## 从复现到独立修改的三步练习

1. 增加端点输入：`x == lower` 和 `x == upper`，先手写预期结果，再运行候选。
2. 增加全负数区间，例如从-8到-2，并分别检查区间外与区间内的值。这样可以揭示只适合零下界的隐藏假设。
3. 构造一个返回区间中点的错误实现，预测它会通过哪些例子、违反哪些性质，再交给验证器。这是在测试验证器的区分能力。

参考判断：第一步主要补充边界，第二步改变数据分布，第三步检查测试是否会被另一种错误策略钻空子。它们回答的问题不同，不能用“新增了三个测试”概括全部价值。

自测：为什么不能让生成补丁的系统同时随意放宽测试？因为实现和判定标准会一起漂移。需求确实变化时可以修改测试，但应单独说明理由，并保留原失败案例。

课题连接：数据划分、奖励计算和坐标转换都是适合这种验证方式的模块。开始训练前，用小而清楚的反例检查这些确定性程序，常常比等到训练曲线异常后再排错更直接。
