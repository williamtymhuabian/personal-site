学习版修订：2026年10月24日。

学习助手今天知道你只想学20分钟，下次却又安排了一小时。它可能保存过这条偏好，但没有检索到；也可能找到了旧记录，没识别出哪条仍然有效。“存过”距离“用对”还有一整段工程链路。

这一篇阅读李博杰《深入理解 AI Agent：设计原理与工程实践》PDF v1.3（2026-07-30）的第3章“用户记忆和知识库”，书内第72—102页，对应 PDF 第80—110页。本文重新组织概念，并配有独立编写的教学练习。

## 先区分两种需要记住的东西

本章的学习目标是搭起一条完整知识链：信息从哪里来，怎样保存，什么时候被检索，如何送入当前上下文，最后怎样证明被正确使用。第二章讨论一次决策的输入，这一章把视角扩展到跨会话的存储与更新。

用户记忆记录与某位用户有关的信息，例如阅读偏好、已确认的计划和长期目标。知识库保存任务可用的资料，例如教材、项目说明和操作规范。两者都要回答“什么时候取回哪条信息”，但访问范围、更新来源和保留期限可能不同。

“共享知识库”也不意味着对所有人公开。团队资料可能只在某个项目内共享；个人记忆则需要按用户隔离。检索排序再准确，也不能弥补把别人的私有记录放进候选集的错误。

可以把一条记忆写成：内容、适用对象、来源、确认状态、有效时间。比如“本月希望每次学习20分钟”就比“喜欢短内容”更明确：前者带有时间和场景，后者可能被错误推广到所有任务。

记忆还需要修改和删除。用户纠正偏好后，只把新记录追加进去，会让旧规则继续参与检索。删除时也要考虑派生摘要、索引和缓存，不能只移走原始对话却留下从中提取的敏感事实。

## RAG 的关键在于把证据送到正确的位置

RAG 将外部检索结果提供给生成过程。一个基本链路可以按文档解析、分块、建立检索表示、找候选、重排序、组装证据和生成回答来理解。

分块决定检索的单位。块太小，可能只剩“按新规则执行”，却丢了前文的新规则；块太大，相关证据又会被大量无关内容包围。好的切分需要保留标题、所属章节、表格上下文及可定位来源。

关键词检索适合精确术语、编号和名称，语义检索有助于处理不同表述。混合检索可以汇集两类候选，再通过重排序缩小证据集。向量相似度提供的是相关性线索，不是事实正确性的证明，更不是最终答案的置信概率。

评价时也应拆开看：正确材料有没有进入候选集，排序后有没有被保留，模型有没有忠实使用材料。如果材料根本没找到，改回答提示词通常修不好上游问题；如果已经找到但引用错误，就要检查生成与证据对应关系。

## 什么时候需要图和更深的索引

第三章进一步讨论层次摘要、实体关系网络和文件系统组织。它们可以帮助表示“细节属于哪个主题”和“多个实体怎样关联”，尤其适合需要跨材料整合的问题。

例如，“哪几篇笔记讨论了同一套评估方法”可以通过关系索引缩小范围。但图中的边同样需要来源与时间：模型抽取了一个关系，不代表关系一定成立。结构化索引提供了额外的组织能力，也带来抽取、更新和核对成本。

智能体化检索则允许系统根据已有结果继续查询、改写问题或补充证据。判断是否采用这种模式，要比较检索质量的收益和额外调用成本；一次检索已经足够的任务，没有必要强行变成长循环。

## 从一条原始记录到一条可用记忆

用户说“这两周我准备考试，每次只学20分钟”。原始对话是一条事件；“近期学习时长为20分钟”是从事件中提取的事实；“安排复习时先确认剩余时间”则是行为建议。它们分别接近情景、语义和程序性知识，不能在提取时混成一条永久偏好。

可以为它保留：记忆标识、对象、内容、来源、记录时间、生效范围、确认状态和替代关系。对象回答“属于谁”，范围回答“在哪种任务里适用”，时间回答“现在还有效吗”。这些字段比一个模糊的相关度分数更早决定能不能使用。

更新也不只是插入新文本。两周后用户改成每次40分钟，应让旧记录失效或标明被新记录替代，同时保留必要的变更依据。仅按写入时间选最新记录仍可能出错：刚导入的旧笔记，写入时间新，事实发生时间却旧。

### 分块怎样影响检索结果？

设想一份规范写着：“一般学习任务为40分钟。考试周例外，改为20分钟。”如果在两句之间切块，检索可能只拿到一般规则，或只拿到缺乏适用对象的例外。

因此，分块不是简单每隔固定字数切一次。应尽量保留标题、条件、表格说明和章节归属；必要时在块中附带父级标题。重叠能减少边界断裂，也会引入重复候选，需要在组装证据时处理。

检索单位和生成单位也不必相同：可以先用小块定位，再按需取回相邻段落或父章节。这样先获得定位精度，再补解释所需上下文，但要重新检查父级内容是否仍在访问范围内。

### 召回、排序与回答分别怎样检查？

假设人工为一道问题标出了两块必要证据。检索返回5块，其中只包含1块必要证据，那么本次 Recall@5 是1/2。即便第一个候选看起来非常相关，另一块关键限制仍然缺失。

重排序关心候选中的好证据能否排到前面，答案评估关心模型有没有正确使用证据。一个方法可能召回提高，但把无关内容也大量送入模型，最终回答反而变差。评价链路应分别记录候选、入选证据和最终引用。

上面的1/2是人为设定的算术例子，不是本文脚本的性能。如果问题没有可靠的相关性标注，先建立少量可人工复查的题目，比直接汇报一个无法解释的检索分数更有帮助。

### 图检索适合哪些问题？

如果问“这条恢复策略来自哪个失败案例，又依赖哪次标定”，关系索引可以把策略、案例和标定版本连接起来。图的每条边仍要有依据；边过时后，依赖它的结论也可能需要撤回。

向量检索和图检索可以协作：先找到语义相关实体，再沿带来源的关系补齐证据。也可以反过来先按结构约束缩小范围，再做语义排序。先比较简单基线，才能知道额外结构是在补什么缺口。

## 离线练习：把可见性与相关性拆开

下面用四条虚构记录演示最小链路：按用户、有效期和确认状态过滤，再做显式关键词集合匹配。没有调用模型、向量数据库或真实个人资料。

保存为 `memory_retrieval.py`，使用 Python 3.10 或以上运行 `python memory_retrieval.py`。

```python
"""Chapter 3: fictional records, lexical search, no LLM or vector database."""
from datetime import date


def visible_records(records, user, today):
    return [r for r in records
            if r["owner"] in (user, "public")
            and r["valid_until"] >= today
            and r["verified"]]


def retrieve(records, query_terms, limit=2):
    ranked = sorted(records,
                    key=lambda r: (-len(set(r["terms"]) & set(query_terms)),
                                   r["id"]))
    return [r for r in ranked if set(r["terms"]) & set(query_terms)][:limit]


if __name__ == "__main__":
    records = [
        {"id": "old", "owner": "reader-a", "terms": ["学习", "时间"],
         "text": "旧计划：每次60分钟", "valid_until": date(2026, 10, 1),
         "verified": True, "source": "练习用旧计划"},
        {"id": "current", "owner": "reader-a", "terms": ["学习", "时间"],
         "text": "当前计划：每次20分钟", "valid_until": date(2026, 12, 31),
         "verified": True, "source": "练习用读者确认记录"},
        {"id": "private-b", "owner": "reader-b", "terms": ["学习", "时间"],
         "text": "另一位读者的私有计划", "valid_until": date(2026, 12, 31),
         "verified": True, "source": "练习用他人私有记录"},
        {"id": "untrusted", "owner": "public", "terms": ["学习", "时间"],
         "text": "未经核实的修改建议", "valid_until": date(2026, 12, 31),
         "verified": False, "source": "练习用外部材料"},
    ]
    visible = visible_records(records, "reader-a", date(2026, 10, 23))
    hits = retrieve(visible, ["学习", "时间"])
    assert [r["id"] for r in hits] == ["current"]
    for item in hits:
        print(item["text"] + "；来源：" + item["source"])
    print("无匹配时返回：", retrieve(visible, ["图像"]))
```

### 一次正常运行的输出

下面是配套脚本本次实际运行的输出，输入为程序内明确构造的教学数据。

```text
当前计划：每次20分钟；来源：练习用读者确认记录
无匹配时返回： []
```

输出只应保留当前读者有效的20分钟计划，同时带上来源；无关查询返回空列表。旧记录、他人私有记录和未经核实的修改建议不会进入最终候选。

这个程序只演示过滤顺序和信息定位，并没有实现完整的记忆系统或 RAG。尤其要注意：示例的 `verified` 是可信程序设置的固定字段，不能让外部文档自己声称“我已核实”，就获得同等信任。

接着可以做三个改动：调整查询词，观察精确匹配的局限；增加两条同时有效但相互矛盾的计划，设计冲突提示；删除当前计划，检查系统是否应该回答“没有可用记录”。不要让检索缺口被模型用猜测填满。

### 逐步读懂代码

代码中的顺序值得逐行跟踪。`visible_records` 先检查 `owner`、`valid_until` 与 `verified`，`retrieve` 再计算查询词与记录词集合的交集数量。第一次排序不是授权检查，真正的可见性过滤在调用它之前已经发生。

排序键前面的负号让交集更多的记录排在前面，后面的 `id` 用于稳定处理同分。`limit=2` 只限制返回条数，不会强行补足2条；没有词汇交集时返回空列表。

不要把 `public` 或 `verified=True` 理解成任何外部文档都能自己设置的权限。示例把这些字段写在可信的构造数据里；真实系统应由身份与资料管理层决定可见范围和核对状态。

它也没有处理生效起点、两个有效记录互相矛盾、自动到期清理或删除后的缓存一致性。发现这些缺口不是练习失败，而是你开始能从简单函数看出完整系统需要哪些责任边界。

## 把检索结果变成可追溯的学习记录

一次好的学习记录可以同时写下：希望记住的知识、适用条件、资料位置，以及以后什么情况下需要更新。比如“记忆检索前先检查访问范围和有效期”，比“今天看了 RAG”更容易转化成实际设计。

留下一个问题：当资料版本变了，你的系统如何找到并撤回依赖旧资料的结论？它会影响的不只是索引，还有以后使用这些结论的每一次回答。

## 练习进阶与参考答案

1. 词汇局限：把查询词改成“复习安排”，保持记录词为“学习、时间”。此时空结果反映词表不匹配，不代表资料中没有答案。可以先扩充受控同义词，再与语义检索方案比较。
2. 冲突处理：构造两条同时有效、分别写20分钟和40分钟的计划。合理行为是检查适用时间与对象、报告冲突或要求确认，不能只取排序第一条当成最终事实。
3. 时效测试：把查询日期改到旧记录有效期内，再改到所有记录都过期以后。分别解释候选集如何变化，确认日期是实验输入，而不是结果出来后才调整的条件。

自测：为什么先拿全库做排名，再把他人记录从答案里删掉仍然不够？因为不该访问的信息已经进入检索处理甚至模型上下文，最终不展示并不能撤销访问。

自测：检索到一条来源明确的记录，能不能直接当作真相？还要检查来源可信度、版本、适用条件以及是否有相反证据。来源可定位只是可核查的起点。

课题连接：给机器人保存“杯子在桌子左侧”的记忆时，还需要观察时间、坐标参考、物体身份和失效条件。物体移动以后，历史记录仍有研究价值，却未必还能直接指导动作。可继续对照 [VLA 记忆题材](#/post/vla-research-topics-and-starter-experiments)。
